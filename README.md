# 안전보건 제안 시스템 구축 가이드 (v4)

모바일에서 **안전 개선제안**과 **아차사고 신고**를 접수하고, 소속별 관리자·사업팀·본사가 같은 주소에서 로그인해 확인·처리하는 시스템입니다.

- 화면(프론트엔드): 이 저장소의 `docs/` 폴더를 **GitHub Pages**로 배포합니다. 주소 하나로 모든 사용자가 접속합니다.
  - 근로자·관리자·사업팀: **모바일 화면**
  - 본사: **PC 관리 콘솔** (가로 900px 이상 화면에서 자동 전환, 엑셀 다운로드·백데이터 업로드)
- 서버(데이터 저장·로그인): **Supabase**를 씁니다. 데이터베이스, 로그인, 사진 저장소, 서버 함수를 제공합니다.
- 입력하는 개인정보는 **사번 + 본인이 정한 비밀번호**뿐입니다. 모든 조직 구분(사업팀·그룹·팀·파트)은 **사번으로만** 이뤄지며, 근로자 화면에는 소속이 표시되지 않습니다.

> 처음 해보는 분도 따라할 수 있도록 클릭 순서대로 적었습니다. 전체 소요 시간은 30~60분 정도입니다.
> Supabase와 GitHub 화면의 메뉴 이름은 업데이트로 조금씩 바뀔 수 있습니다. 이름이 다르면 비슷한 메뉴를 찾으면 됩니다.

## 1. 사용자 구분과 조직 구조

### 조직 구조
```
본사 (대표이사 산하 본사 부서 · 노동조합 등)
└─ 사업팀 › 그룹 › 팀 › 파트     ← 인사 부서코드 기준 (예: AHA000 › AHB000 › AHB010 › AHB010-A1)
```
- 조직도는 **인사 명단의 부서코드 · 부서 · 상위부서**로 만들어집니다. 본사 PC 콘솔 **[백데이터 업로드]** 에 인사 시스템의 사원 명단 엑셀을 그대로 올리면 조직도(`org_units`)와 사번별 소속이 한 번에 반영됩니다.
- 이름이 '사업팀'으로 끝나는 최상위 부서는 **사업팀**, 그 밖의 최상위(대표이사 등)와 하위 부서는 **본사**로 묶입니다.
- 업로드 때 서버로 가는 정보는 **사번(서버에서 암호화) · 성명(가운데 마스킹) · 부서코드**뿐입니다. 주민번호·연락처·주소 등 다른 열은 브라우저에서도 읽지 않습니다.
- 제출건은 제출 시점의 작성자 사번 소속(사업팀·그룹·팀·파트)으로 **서버가 자동 분류**합니다. 근로자는 소속을 고르지도, 보지도 않습니다.

### 사용자 4단계

| 사용자 | 소속 | 볼 수 있는 범위 | 처리 | 인원관리 |
|---|---|---|---|---|
| **근로자** | 부서코드 | 본인 제출건만 (소속 표시 없음) | - | - |
| **관리자** | 그룹 · 팀 · 파트 중 하나 | **본인 소속 조직과 그 하위만** (그룹 관리자=그룹 전체, 팀 관리자=팀 전체, 파트 관리자=파트만) | 범위 내 건 처리 | 범위 내 **근로자** 등록·관리 |
| **사업팀** | 사업팀 | 소속 사업팀 전체 (그룹·팀·파트별 필터) | 사업팀 내 건 처리 | 사업팀 내 **근로자·관리자** 등록·관리 |
| **본사** | - | 전사 (PC 콘솔) | 전체 처리, 삭제 | 모든 사용자 등록·관리, **백데이터 업로드** |
- 모든 조회·등록·결재 권한은 **본사 › 사업팀 › 그룹 › 팀 › 파트** 상하 관계를 따르며, 위 단계는 아래 단계를 모두 볼 수 있고 아래 단계는 위나 옆 조직을 볼 수 없습니다.
- 권한은 화면이 아니라 **데이터베이스 규칙(RLS)** 으로 막습니다. 화면 코드를 고쳐도 범위 밖 데이터는 서버가 내주지 않습니다.

### 화면 구성
| 사용자 | 하단 메뉴 |
|---|---|
| 근로자 (모바일) | 작성 · 내 제출내역 |
| 관리자 · 사업팀 (모바일) | 현황 · 접수목록 · 인원관리 · 작성 |
| 본사 (PC) | 대시보드 · 접수 관리 · 조직·인원(사번 등록·조회 팝업) · 비밀번호 관리 · 백데이터 업로드 |
| 본사 (휴대폰) | 관리자 화면과 같은 모바일 화면 |

### 입력 항목
| 개선제안 | 위험성평가 참여 | 아차사고 신고 |
|---|---|---|
| ① 제안 등급 (가·나·다·라) * | ① 장소 (근무지) * | ① 발생 일시 * |
| ② 장소 * | ② 위험요인 (사고 유형과 같은 목록, 차후 등록 예정) | ② 장소 * |
| ③ 상세 내용 * | ③ 내용 * | ③ 사고 유형 (차후 등록 예정) |
| ④ 조치 요청사항 | ④ 위험정도 상·중·하 * | ④ 상황 설명 * |
| ⑤ 사진 첨부 | | ⑤ 재발 방지 의견 |
| | | ⑥ 사진 첨부 |

- **작성자 수정**: 근로자는 결재 전(관리자가 '검토중' 등으로 처리하기 전, '접수' 상태)까지 본인 제출건의 내용을 고칠 수 있습니다(사진 제외). 수정 내역은 처리 이력에 '내용 수정'으로 남습니다. 관리자는 제출 내용을 바꿀 수 없습니다.
- **처리 이력 삭제 (관리자 이상)**: 상세 화면 처리 이력의 ✕로 삭제합니다. **가장 최근 처리를 지우면 제출건이 직전 상태로 되돌아갑니다**(예: '검토중' 삭제 → '접수' → 작성자가 다시 수정 가능). 최초 '접수' 기록은 지울 수 없습니다.
- **위험성평가 참여 처리**: 관리자는 **검토중 → 반영 완료**로 처리하며, 반영 완료 시 **반영 위험정도(상·중·하)** 를 반드시 선택합니다. 조직 분류·권한 범위는 개선제안·아차사고와 같습니다.

`*` 필수. 사고 유형 목록이 정해지면 `config.js`의 `NEARMISS_CATEGORIES`에 넣으면 바로 선택할 수 있게 됩니다.

## 2. 제안 등급과 처리 흐름

| 등급 | 적용 범위 |
|---|---|
| **가** | 전사 적용 |
| **나** | 사업팀 적용 |
| **다** | 그룹 적용 |
| **라** | 단순 조치 |

```
근로자 제출 (제안 등급 선택)
   ↓
[접수] → [검토중] → ┬→ [반려]                                     (종료)
                   └→ [조치완료] + 결정 등급 선택
                         ├ 라등급      → 조치완료                    (종료)
                         └ 가·나·다등급 → 산업안전보건위원회 의결예정  (종료)
```

- **제안 등급**: 근로자가 제출할 때 직접 고릅니다.
- **결정 등급**: 처리자(관리자·사업팀·본사)가 [조치완료]를 고를 때 반드시 선택합니다. 기본값으로 근로자의 제안 등급이 들어가 있습니다.
- **가·나·다등급으로 결정하면** 저장할 때 상태가 자동으로 **"위원회 의결예정"** 으로 바뀌고 종료됩니다. 라등급만 일반 조치완료로 종료됩니다. 이 규칙은 서버에서 강제되어 화면과 상관없이 항상 적용됩니다.
- 아차사고는 등급 없이 접수 → 검토중 → 조치완료로 처리합니다.
- 모든 상태 변경·결정 등급·의견은 **처리 이력**에 자동으로 남고, 근로자도 [내 제출내역]에서 결과와 의견을 볼 수 있습니다.

## 3. 전체 구조와 사번·성명 보호 방식

**성명 (본사 화면 표시용)**
- 본사가 백데이터 엑셀에 성명을 넣으면, **브라우저에서 먼저 마스킹**(홍길동 → 홍\*동, 남궁민수 → 남\*\*수, 이산 → 이\*)한 뒤 서버로 보냅니다. 서버 함수도 한 번 더 마스킹해서 저장하므로, **원래 성명은 서버 어디에도 남지 않습니다.**
- 마스킹 성명은 본사 PC 화면(조직·인원, 비밀번호 관리, 접수 관리의 제출자, 엑셀)에서만 보입니다. 근로자 화면에는 표시되지 않습니다.


```
 ┌─────────────────────┐         HTTPS(암호화 통신)         ┌──────────────────────────────┐
 │  휴대폰 (같은 주소)   │ ─────────────────────────────────▶ │           Supabase            │
 │  GitHub Pages       │  ① 사번 → 서버 함수(api)             │  [Edge Function "api"]       │
 │  index.html         │     사번을 비밀키로 암호화             │   사번 → HMAC-SHA256 해시     │
 │                     │  ② 제안 등록·조회·처리               │  [Database]                  │
 │  로그인 계정의 권한에  │     (권한 규칙 RLS가 범위 자동 검사)   │   org_units  : 조직도(부서코드)│
 │  따라 화면이 바뀜     │  ③ 사진 업로드 (비공개 저장소)         │   employees  : 사번해시·권한·소속│
 └─────────────────────┘                                     │   reports    : 제안·신고       │
                                                             │   report_logs: 처리 이력       │
                                                             │  [Storage] report-photos     │
                                                             └──────────────────────────────┘
```

**사번 처리**
```
사번 "20240101" ─(HTTPS)→ 서버: HMAC-SHA256(사번, 비밀키 EMP_PEPPER) → "7f3a9c21…(64자리)" 저장 → 화면 표시 "7F3A9C21"
```
- 원래 사번은 어디에도 저장되지 않으며 되돌릴 수 없습니다. 비밀키는 서버에만 있어 사번 대입 공격도 막힙니다.
- 목록에는 **식별코드(8자리)** 만 보입니다. 특정인의 제출건은 [인원관리 → 사번 조회]로 찾습니다. **원본 사번 명단은 사내에 별도 보관**하세요.
- 로그인 ID는 해시로 만든 가상 주소(`u7f3a…@emp.ehs.local`)를 씁니다. 실제 메일은 발송되지 않습니다.
- 첨부 사진은 업로드 전에 휴대폰에서 다시 압축해 **위치정보(GPS) 등 메타데이터를 제거**합니다.
- 법적으로는 **가명정보**(원본 명단과 대조하면 식별 가능)에 해당하니, 개인정보 안내와 사내 정보보안 승인은 별도로 챙겨주세요.

## STEP 2. 데이터베이스 만들기 (SQL 실행)

> **v1을 이미 설치했다면** 먼저 `supabase/reset.sql`을 같은 방법으로 1회 실행하세요. (기존 데이터가 삭제되므로 운영 전에만 사용)
> **v2·v3를 설치했다면** reset 없이 `schema.sql`만 다시 실행하면 v4(부서코드 조직도·상하 권한·아차사고 장소)로 업그레이드됩니다. 기존 데이터는 유지됩니다. 업그레이드 후 **STEP 4 서버 함수도 새 코드로 다시 Deploy**하고, 본사 콘솔에서 **인사 명단을 한 번 업로드**해야 관리자 범위가 조직도 기준으로 동작합니다.

1. 왼쪽 메뉴 **SQL Editor** → **New query**
2. `supabase/schema.sql` 전체를 복사해 붙여넣기 → **Run**
   - "destructive operation" 확인창이 뜨면 **Run this query**를 누르세요.
3. 결과에 `org_units 0`, `employees 0`, `reports 0`, `report_logs 0`이 보이면 성공입니다. (조직도는 STEP 8에서 인사 명단을 올리면 채워집니다)

이 SQL이 만드는 것: 조직도(부서코드 트리), 인원·제안·이력 테이블, 범위별 권한 규칙, 등급·위원회 자동 처리 규칙, 백데이터 일괄 반영 함수, 비공개 사진 저장소(1장당 5MB).

## STEP 5. 비밀키(Secrets) 등록

**Edge Functions** → **Secrets** 에서 추가합니다.

| 이름(Key) | 값(Value) | 설명 |
|---|---|---|
| `EMP_PEPPER` | 40자 이상 임의 문자열 | 사번 암호화 비밀키. **가장 중요** |
| `INITIAL_ADMIN_EMP_ID` | 본인 사번 | **최초 본사 계정**. 본사 계정이 하나도 없을 때만 쓰입니다 |

**EMP_PEPPER 만드는 법**: PC 크롬에서 `F12` → **Console** 탭 → 아래 한 줄 붙여넣고 Enter → 나온 64자리 문자열을 등록하고 사내에 백업
```js
Array.from(crypto.getRandomValues(new Uint8Array(32)), b => b.toString(16).padStart(2,'0')).join('')
```
> ⚠️ **EMP_PEPPER는 절대 바꾸거나 잃어버리면 안 됩니다.** 바뀌면 모든 사번 등록이 무효가 되어 전원이 다시 등록해야 합니다. 외부에 공유하지 마세요.

## STEP 8. 계정 만들기 (본사 → 사업팀 → 관리자 → 근로자)

### 1) 최초 본사 계정
PC 또는 휴대폰으로 주소 접속 → **[최초 등록]** → 본인 사번(`INITIAL_ADMIN_EMP_ID`) + 비밀번호(8자 이상) → 상단에 **본사** 표시가 나오면 성공입니다.

### 2) 사번 등록은 위에서 아래로
**조직 백데이터 업로드(본사, 권장)**: 본사 PC 콘솔 → **백데이터 업로드** → 인사 시스템의 사원 명단 엑셀(사원번호·성명·부서코드·부서·상위부서 열 포함)을 그대로 선택하거나 [업로드 양식 다운로드]의 양식을 채워 선택 → 미리보기 확인 → **서버에 반영하기**. 조직도가 만들어지고, 신규 사번은 근로자로 등록, 기존 인원은 소속이 갱신됩니다. 재직여부 열이 있으면 재직자만 반영합니다.
  - **권한은 직책으로 자동 설정**됩니다: 사업팀장과 사업팀 소속 **1~4지원그룹 인원 전부 → 사업팀**, 그룹장 · SE팀장 · SE파트장 → **관리자**(본인 소속 그룹·팀·파트와 그 하위), 그 외 → **근로자**.
  - **본사 권한은 업로드로 주거나 바꾸지 않습니다.** [조직 · 인원]에서 별도로 지정하세요. 다시 업로드하면 본사 외 권한은 직책 기준으로 다시 맞춰집니다.

**개별 등록**: 본사 PC는 **조직·인원 → [＋ 사번 등록]** 팝업, 모바일은 **인원관리 → 사번 등록**에 사번을 붙여넣고(엑셀 사번 열 복사 가능) 권한과 소속을 고른 뒤 **일괄 등록**합니다.

| 등록하는 사람 | 등록할 수 있는 대상 |
|---|---|
| 본사 | 본사 · 사업팀(사업팀 선택) · 관리자/근로자(사업팀별 색상으로 구분된 그룹 → 팀 → 파트 지정) · 백데이터 일괄 업로드 |
| 사업팀 | 소속 팀 그룹의 관리자 · 근로자 |
| 관리자 | 소속 그룹의 근로자 |

권장 순서: 본사가 **백데이터로 전 직원 사번·소속을 일괄 등록** → 사업팀 담당자 계정은 본사가 개별 등록 → 관리자 권한은 백데이터의 권한 칸 또는 [조직·인원]에서 지정. 각 단계에서 대상자에게 "주소 접속 → [최초 등록] → 사번과 비밀번호 입력"을 안내합니다.

> 💡 **등록 후 빨리 가입하도록 안내하세요.** 미가입 상태에서는 그 사번을 아는 다른 사람이 먼저 가입할 수 있습니다. 문제가 생기면 관리자가 **비밀번호 초기화** 후 본인이 다시 가입하면 됩니다.

## 데이터 내보내기와 실명 치환 (KEY 리스트)

전체 흐름은 **데이터 파일 + KEY 파일 → 오프라인 정리 도구** 하나입니다.

| 단계 | 누가 · 어디서 | 하는 일 | 파일에 든 정보 |
|---|---|---|---|
| ① 데이터 받기 | 사업장 관리자 · 휴대폰 | 접수목록 → **[내보내기]** → 공유하기(회사 메일 등) / 휴대폰에 저장 / CSV | 식별코드 + 가린 성명(홍\*동)만 |
| ② KEY 발급 | 본사 · PC 콘솔 **[KEY 리스트]** | 인사 명단(사원번호·성명) 선택 → 비밀번호·사용 기한 → 사업장별 **KEY 받기** | 그 사업장 인원의 식별코드 → 사번·성명 (비밀번호로 암호화) |
| ③ 전달 | 본사 → 사업장 | KEY 파일은 메일 등으로, **비밀번호는 전화·문자 등 다른 경로**로 | |
| ④ 치환 | 사업장 PC · **오프라인 정리 도구** | ① 데이터 파일 ② KEY 파일 + 비밀번호를 넣으면 식별코드가 사번·성명으로 바뀜 → 정리 엑셀 저장 | 인터넷 없이 PC 안에서만 처리 |

- **KEY 파일**: `KEY_사업팀_그룹_날짜.ehskey`. AES-256-GCM(PBKDF2-SHA256 25만 회)으로 암호화되어 비밀번호 없이는 열 수 없습니다. 그 사업장(그룹)에 지금 속해 있거나 그 사업장에서 제출한 적이 있는 인원만 담깁니다. **사용 기한**(7·30·90·180일)이 지나면 정리 도구가 열지 않습니다.
- **본사 PC에서 KEY를 만들 때**: 인사 명단은 브라우저에서 사원번호·성명 두 열만 읽고, 서버에는 **사번만** 보내 식별코드와 소속을 확인합니다. 성명은 PC 밖으로 나가지 않습니다. 발급할 때마다 `export_logs`에 누가·언제·몇 명을 대조했는지만 남습니다(본사만 열람).
- **오프라인 정리 도구**(`docs/ehs-offline.html`, 본사 콘솔 [KEY 리스트] → [오프라인 정리 도구 받기]): HTML 파일 1개로, 외부 통신이 차단되어 있고(CSP) 넣은 파일은 창을 닫으면 사라집니다. 접수 내역/제출자별 집계, 필터, 상세 보기, 정리 엑셀 저장을 지원합니다.
- 본사는 콘솔 접수 관리·조직·인원의 **[실명 포함 엑셀]**로 인사 명단과 바로 대조해 받을 수도 있습니다.
- 사번 암호화 비밀키(EMP_PEPPER)는 서버에만 있으므로, KEY 없이는 식별코드를 사번으로 바꿀 수 없습니다.
- 정리 도구 소스: `tools/offline/app.js`, 다시 만들기: `npm i xlsx` 후 `python3 tools/offline/build.py <xlsx.full.min.js 경로>`

- 2026-11 기준 갤럭시 설치는 **Chrome 앱 설치** 방식으로 통일했습니다. 설치 파일 경고·보안 설정 변경이 없고 화면·아이콘 변경이 자동 반영됩니다. 아래 APK 빌드는 필요할 때를 대비해 남겨 둡니다.

- **서명키**: 저장소 **Settings → Secrets and variables → Actions**에 `ANDROID_KEYSTORE_B64`, `ANDROID_KEYSTORE_PASSWORD`가 등록되어 있어야 빌드됩니다. 서명키 원본(`ehs-proposal.keystore`)과 비밀번호는 사내에 백업하세요. **잃어버리면 기존 설치 앱을 업데이트할 수 없어** 전원이 지우고 다시 설치해야 합니다. 저장소에는 절대 올리지 마세요.
- **주소줄 없애기(선택)**: 지금은 앱 위쪽에 얇은 주소줄이 보일 수 있습니다. `gmazellan123-byte.github.io` 이름의 공개 저장소를 만들고 `.well-known/assetlinks.json`(아래 내용)과 빈 `.nojekyll` 파일을 올린 뒤 Pages를 켜면, APK를 다시 만들지 않아도 주소줄이 사라집니다.

  ```json
  [{"relation":["delegate_permission/common.handle_all_urls"],
    "target":{"namespace":"android_app","package_name":"io.github.gmazellan123byte.ehsproposal",
      "sha256_cert_fingerprints":["7F:65:42:0F:86:2A:3F:EC:58:D0:18:91:78:83:50:DC:A1:EF:4B:66:6A:65:56:BD:12:14:56:DE:0B:58:82:DB"]}}]
  ```
- 업무폰 보안 정책(MDM)으로 외부 APK 설치가 막힌 현장은 웹 주소나 홈 화면 추가 방식을 쓰세요.

| 엑셀 보고 | 본사 PC: [전체 데이터 엑셀](조직별현황·접수목록·등급현황·월별추이 4개 시트), [조회 결과 엑셀], [조직별 현황 엑셀], [인원 목록 엑셀] / 모바일: 접수목록 [엑셀] |
| 조직 변경 (인사이동·팀 개편) | 본사 PC → 백데이터 업로드로 최신 명단을 다시 올리면 소속이 갱신됨. 업로드할 때마다 **반영 이력**(일시·반영 대상·신규·갱신·오류·반영 후 인원·반영자)이 남고, [조직 · 인원] 머리말에 마지막 반영 일시가 표시됨 |
| 연·월별 이력 보기 (모바일) | 관리자 이상 → 접수목록 → **연도·월** 선택 (접수일 기준). [내보내기]도 선택한 기간만 내보냄 |
| 특정 직원 제출건 (포상 등) | 인원관리 → 사번 조회 → **제출건 보기** |
| 비밀번호 분실 | 본사 PC → **비밀번호 관리**: 목록의 [초기화], 여러 명 체크 후 [선택 초기화], 또는 사번 입력 후 [사번으로 초기화] (근로자·관리자·사업팀 대상). 모바일 관리자는 인원관리 → 관리 → 비밀번호 초기화. 초기화 후 본인이 [최초 등록]으로 새 비밀번호 설정 |
| 인사이동 | 인원관리 → **관리** → 권한·소속 변경 (본인 범위 안에서만 가능) |
| 퇴사 | **관리 → 사용 중지** 또는 등록 삭제. 어느 쪽이든 제출건은 **최초 등록한 부서(제출 당시 조직)**에 남고, 식별코드와 제출 당시 성명(가림)도 유지됨 |
| 사고 유형 등록 | `config.js`의 `NEARMISS_CATEGORIES` 수정 후 GitHub에 다시 업로드 |
| 부서 신설·이름 변경·조직 개편 | 인사 명단을 다시 업로드하면 조직도와 인원 소속이 자동 갱신됨 (부서코드 기준). **이미 제출된 건은 바뀌지 않고** 최초 등록한 부서(제출 당시 조직)에 남음 |
| 로고 교체 | 로고는 `docs/index.html`에 이미지 데이터로 내장되어 있습니다 (`var LOGO = 'data:image/png;base64,…'`) |

### 무료 플랜 주의사항
- **Supabase 무료 프로젝트는 일주일간 사용이 없으면 자동 일시정지**됩니다. 데이터는 남지만 대시보드에서 **Restore**를 눌러야 다시 접속됩니다. 정식 운영 단계에서는 유료(Pro) 플랜을 검토하세요(일시정지 없음, 매일 백업).
- 무료 용량: DB 500MB, 파일 1GB. 사진은 1장당 약 0.2~0.5MB로 압축됩니다.
- 월 1회 정도 CSV를 내려받아 사내에 보관하세요.

## 문제 해결

| 증상 | 원인과 해결 |
|---|---|
| "데모 모드"가 계속 보임 | `config.js`의 URL/KEY가 비어 있거나 반영 전. 1~3분 뒤 새로고침 |
| "서버에 연결할 수 없습니다" | ① 함수 이름 `api` 확인 ② `ALLOWED_ORIGIN`이 접속 주소와 정확히 같은지 ③ 프로젝트 일시정지 여부 |
| 401 / Invalid JWT | STEP 4의 **Verify JWT를 OFF** 하지 않음 |
| "EMP_PEPPER가 없거나 너무 짧습니다" | STEP 5 Secrets 미등록 또는 32자 미만 |
| "등록되지 않은 사번입니다" | 소속 관리자가 사번을 등록하지 않음. 최초 본사라면 `INITIAL_ADMIN_EMP_ID`와 입력 사번이 같은지 확인 |
| "관리 범위 밖의 인원입니다" | 정상 동작입니다. 관리자는 자기 사업장 근로자만, 사업팀은 자기 팀만 관리할 수 있습니다. 상위 담당자에게 요청하세요 |
| "조치완료 처리 시 결정 등급을 선택해야 합니다" | 개선제안을 조치완료할 때는 결정 등급이 필수입니다 |
| 엑셀 버튼을 눌러도 반응 없음 | 엑셀 모듈을 처음 한 번 인터넷(cdn.jsdelivr.net)에서 불러옵니다. 사내망에서 차단되면 IT 부서에 허용 요청 |
| 백데이터 "알 수 없는 부서코드" / "부서명이 없음" | 새 부서코드는 같은 행에 부서·상위부서 이름이 있어야 합니다 (양식의 [부서코드(참고)] 시트 참고) |
| 백데이터 "사번 형식 오류" | 사번은 영문·숫자 4~20자만 가능합니다 (`T_01` 같은 밑줄 포함 테스트 계정은 제외됨) |
| 본사인데 PC 콘솔이 안 열림 | 브라우저 창 가로가 900px 이상이어야 합니다. 창을 넓힌 뒤 새로고침 |
| 로그인 후 "권한이 없습니다" | STEP 2 SQL이 끝까지 실행됐는지 확인 (다시 실행해도 데이터는 지워지지 않습니다) |
| 사진 업로드 실패 | 촬영 제한 사업장일 수 있으니 사진 없이 제출. 반복되면 Storage에 `report-photos` 버킷 확인 |
| 그 외 서버 오류 | Edge Functions → `api` → **Logs** 확인 |

## 보안 점검표와 한계

**운영 전 체크리스트**
- [ ] 사내 정보보안팀에 외부 클라우드(Supabase, 미국 법인) 사용 가능 여부 확인
- [ ] 고객사(현장) 보안 규정상 촬영·업로드 제한 여부 확인
- [ ] 개인정보 처리 안내(수집 항목: 사번(가명처리), 목적, 보관기간) 게시
- [ ] `EMP_PEPPER` 사내 백업, 외부 미공유
- [ ] Authentication의 **Allow new users to sign up = OFF**
- [ ] service_role / secret 키가 GitHub에 올라가지 않았는지 확인
- [ ] 원본 사번 명단은 사내 PC에만 보관

**알고 있어야 할 한계**
- 사번+비밀번호 방식은 **미가입 사번을 다른 사람이 먼저 가입(선점)** 할 수 있습니다. 등록 즉시 가입 안내, 이상 시 초기화로 대응합니다.
- 공개 주소이므로 누구나 로그인 화면은 볼 수 있습니다. 데이터는 로그인 + 범위 규칙으로 보호됩니다.
- 관리자 휴대폰 분실 시 상위 담당자가 해당 사번을 **사용 중지**하세요.
- 상세 내용 칸에 직원이 이름·연락처를 직접 적으면 그대로 저장됩니다. 화면 안내로 주의를 주세요.

## 파일 구성과 데이터 구조

```
(저장소)
├─ README.md                      ← 이 가이드
├─ docs/                          ← ★ GitHub Pages로 배포되는 화면 (Settings → Pages → /docs)
│   ├─ index.html                 화면 전체 (모바일 4단계 사용자 + 본사 PC 콘솔, 회사 로고 내장)
│   ├─ config.js                  Supabase 주소·키, 아차사고 사고 유형 목록
│   ├─ manifest.webmanifest       홈 화면 추가 정보
│   ├─ icon-192.png / icon-512.png 홈 화면 아이콘
│   └─ .nojekyll                  GitHub Pages 가공 방지용 빈 파일
└─ supabase/                      ← Supabase 대시보드에 붙여넣는 코드 (배포되지 않음)
    ├─ schema.sql                 STEP 2: 조직·테이블·권한·등급 규칙·백데이터 함수·사진저장소
    ├─ reset.sql                  v1 설치 이력이 있을 때만 schema.sql 전에 1회 실행
    └─ functions/api/index.ts     STEP 4: 사번 암호화·가입·범위별 인원관리·백데이터 반영
```

**org_units (조직도)** — `code` 부서코드, `name` 부서명, `parent_code` 상위 부서코드, `path` 최상위부터의 부서코드 경로(하위 판단용), `team/site/dept/part` 단계별 이름

**employees (인원)** — 성명은 마스킹 값만, 연락처 없음
| 컬럼 | 내용 |
|---|---|
| emp_hash / emp_code | 사번 해시 / 식별코드(앞 8자리) |
| role | worker 근로자 / manager 관리자 / team 사업팀 / hq 본사 |
| org_code, org_path | 소속 부서코드와 조직 경로 (권한 범위 판단 기준) |
| team, site, dept, part | 사업팀 · 그룹 · 팀 · 파트 이름 (부서코드에서 자동 입력) |
| name_mask | 마스킹 성명 (예: 홍*동) — 백데이터 업로드 시 브라우저에서 마스킹 후 전송, 원래 성명은 저장하지 않음 |
| active, registered_at | 사용 여부, 가입 일시 |

**reports (제안·신고)**
| 컬럼 | 내용 |
|---|---|
| report_no | 접수번호 |
| type | proposal 개선제안 / nearmiss 아차사고 |
| org_code, org_path, team, site, dept, part | 제출자 소속 (제출 시점의 사번 소속을 서버가 자동 기록) |
| proposed_grade / final_grade | 제안 등급(근로자) / 결정 등급(처리자) : 가·나·다·라 |
| location | 장소 (개선제안 · 아차사고) |
| occurred_at, category | 발생 일시, 사고 유형 (아차사고) |
| detail, request, prevention | 상세 내용·상황 설명 / 조치 요청사항 / 재발 방지 의견 |
| status | received 접수 / reviewing 검토중 / rejected 반려 / done 조치완료 / committee 위원회 의결예정 |
| admin_comment | 처리 의견 (제출자에게 공개) |
| closed_at | 종료 일시 |

**report_logs (처리 이력)** — 상태·결정 등급·의견이 바뀔 때마다 처리자 권한·식별코드와 함께 자동 기록

## GitHub로 수정하는 방법

앞으로의 수정은 이 저장소에서 합니다.

| 하고 싶은 일 | 방법 |
|---|---|
| 설정값 변경 (Supabase 키, 사고 유형 목록) | 저장소에서 `docs/config.js` 열기 → 연필 아이콘(Edit) → 수정 → **Commit changes** → 1~3분 뒤 반영 |
| 화면 기능 수정 | `docs/index.html` 수정 후 커밋. 큰 수정은 Claude에게 저장소를 지정해 요청하면 직접 수정·커밋할 수 있습니다 |
| DB 규칙 변경 | `supabase/schema.sql` 수정·커밋 후, 같은 내용을 Supabase SQL Editor에서 실행 (SQL은 자동 배포되지 않음) |
| 서버 함수 변경 | `supabase/functions/api/index.ts` 수정·커밋 후, Supabase Edge Functions의 `api` 코드에 붙여넣고 Deploy (자동 배포되지 않음) |
| 이전 버전으로 되돌리기 | 저장소 **Commits** 목록에서 원하는 시점의 파일을 확인해 다시 커밋 |

> 화면(`docs/`)만 GitHub에 커밋하면 자동 반영됩니다. **DB와 서버 함수는 Supabase에 직접 적용**해야 한다는 점만 기억하세요.
